When coworkers help

Several parties to represent

Each agent speaks for someone, and none of them can speak for the others.

Conflicting objectives

Real tradeoffs between goals, not one goal split into pieces.

Partial knowledge, on purpose

One agent couldn't, or shouldn't, hold everything.

Membership that changes

Agents join and leave while the task is running.

Cross a team or company boundary, and all four show up at once.

  • Sometimes a swarm is the right fit, or the use case drives the peer-to-peer pattern. Here are some conditions where this is true.
  • (1) Representing multiple parties: each agent speaks for someone, and none can speak for the others. Think of personal agents, like multiple OpenClaw agents collaborating, or similar.
  • (2) Conflicting objectives, where you want to make sure you are making real tradeoffs.
  • (3) Partial knowledge, where you don't or can't have one agent holding everything.
  • (4) And sometimes, membership needs to be highly flexible.
  • In the case of real boundaries between teams or companies, it is hard to have a single orchestrator. You see multiple of these conditions at once. The other side's agent has its own rules and its own owner. Peer to peer isn't a preference here. It's the requirement. (~2.5 min)

Agents agree because the others agreed, not because they checked.

A frame from the Internet of Cognition team

  • Turn that same framing around, and it's where things go wrong.
  • Intent breaks when agents take on goals nobody asked for.
  • Context breaks when one unchecked fact spreads until everyone treats it as true.
  • Reasoning breaks as false consensus: agents agree because the others agreed, not because they checked.
  • In a swarm or peer-agent scenario, when agents are talking to each other, they will coordinate whether you design for it or not.
  • Think of the Hugging Face story, where agents turned a shared repository into their own message board. Nobody designed that. So it's worth designing for. (~0.75 min)

This is not the complete set. It's where we started, and we expect to need more.

  • These are the primitives that we've needed so far, mapped to what Mycelium actually has. The first three are the plumbing.
  • (1) Discover. Mycelium has rooms where you can add members and keep track of work on a board.
  • (2) Share state. The board manages tasks, and every task has a thread. Any member can add memory in markdown format, and decisions are captured in memory too.
  • (3) Mentions and turns. Agents can stay quiet unless woken. We use @ to ask and wake, and Mycelium engines can give agents turns instead of waking everyone at once. We can also assign without waking (@~) and interrupt (@!).
  • Press: then our engines, which we have been building.
  • (4) Align intent. We use ACCORD so the agent team has the same goal, same words, and same definition of done.
  • (5) Negotiate. We use CONCORD and the Aligner so that every agent has a voice and can reach decisions that all agents can accept.
  • ACCORD and CONCORD are based on L9 protocols built by the Internet of Cognition team.
  • This is just our starting set! More are being added that do other important jobs. For example, the Verifier is new: it flags things like an approval that nobody gave. We will keep building more as we need them. But these are the critical ones. (~2 min)

Agree: the toolbox

Conductor

A script for a conversation. It fixes the steps, and at each step it asks certain agents to speak. Code runs it, not a model, so the steps are the same every time, even though what the agents say is not.

Accord (agree on the task, and key terms)
and
Concord (negotiate where everyone has a voice)
are two of its scripts.

@conductor concord @~a @~b: question

Aligner

A lightweight "let's all get along" flow for agents that disagree. It surfaces the disagreements and works toward agreement.

@aligner agree on where we store tokens

Any agent can start one, or you can. Every run is kept.

  • Agreeing. These are engines: tools that you can add to a room.
  • These are key capabilities needed for peer-to-peer agentic systems, and the focus of the rest of this talk.
  • The conductor runs a script: it fixes the steps, and at each step it asks certain agents to speak. Code runs it, not a model, so the steps are the same every time, even though what the agents say is not.
  • Two of its scripts are ACCORD, which gets the agent team to agree on the task and its key terms, and CONCORD, which gives every agent a voice and reaches a decision all of them can accept.
  • The Aligner was our first implementation of a protocol to get multiple agents to negotiate and agree. We have kept it because it is still useful.
  • Agents can start these, or you can.
  • Results from every run are kept in memory. (~1.5 min)

Accord: agree on the task

  • First up, ACCORD. We use ACCORD to get everyone to the same understanding of the task before work starts: what it asks, what is out of scope, what done looks like, and what the key words mean.
  • Members label what they write. Code combines it, not a model. Anything that doesn't line up becomes an open item.

Accord: what happened

Describe

Each member labelled what they think the task is. 20 points in the first round, each in the member's own words.

What's missing

The conductor showed the points so far and asked what was missing. Members added 16 more, for 36 in all. None were combined, because each role raised its own concerns.

The words

Sales and customer success meant different things by "aggressive". Asked again, each stood by its own meaning, so the summary lists both.

Done

One shared summary, saved in the room's memory. It says how "done" was checked, and by whom.

Nobody had the same picture. Now everyone can see where they differ.

  • Say this: Recorded on an earlier build. Now Accord also pins down key terms, with units, and gives every check an owner.
  • (1) Each member described the task in their own words. This was 20 points across the 4 agents. ACCORD keeps each one, and who said it.
  • (2) The conductor shows the points so far and asks if anything is missing. 16 more points were added.
  • (3) All potential key-word conflicts are reviewed. 12 checks here. One conflict remains: sales and customer success mean different things by "aggressive".
  • (4) A summary is written to memory, including the open items: any points that only one agent made, and the word that 2 agents use differently.
  • Now everyone sees where the agents differ. (~1.5 min)

Concord: agree on a decision

  • Concord is for a decision where members want different things.
  • Each agent suggests an option.
  • All agents rate every option from 0 to 100.
  • A fixed rule chooses the option whose lowest rating is highest.
  • Models write the options and ratings, and code decides what happens next.
  • The task here: decide the renewal offer for ACME.
  • Command: @conductor concord @success @finance @sales @legal: Decide the renewal offer for Acme.
  • Play the video (45 seconds), then press on for what happened.
  • Newer build than the video: Concord now leads with reasons, not numbers. Every option and every rating comes with a reason. Each member's ratings are read on their own scale, and the bar is stated in terms of two outcomes everyone rated. The run ends by saying in words who is short and why. The video and recap show the earlier 0 to 100 ratings against a bar of 70. (~2 min with the video)

Concord: what happened

Suggest and rate

Each member suggested one option and rated all four. The rule chose sales's C: 15% off for three years. Finance rated it 40 and legal 55.

First fix

Finance was least happy, so it improved C. Its version, E, capped the discount at 10%. Legal rated E 68, just under the bar of 70.

Second fix

Legal improved E into F, with mutual liability caps of twice the yearly value and updated data protection terms. Everyone rated F 76 or higher. Finance went from 40 to 82.

Done

Everyone was above the bar. Agreed on F after six steps, and saved as the room's decision.

Nobody got steamrolled. The least happy member improved the offer.

  • Say this: Recorded on an earlier build. Now every option and rating comes with a reason, and each member is read on their own scale.
  • (1) The rule picks the option the least happy member likes most, so a majority can't outvote one member's objection.
  • Finance was at 40 on option C, so finance was asked to fix it.
  • Then, in the next round, legal was the least happy, at 68.
  • Each fix made the least happy member better off.
  • We use the least happy member to improve the offer, until we get to a point where all the agents can live with the result. That doesn't mean they all love it.
  • The decision is saved in memory (context/decision/acme-renewal-offer), with every option and rating. (~1.5 min)

Sometimes a swarm is the right fit. Sometimes peers are the requirement.
Cross a boundary and nobody can be the orchestrator. Then you need to discover, share state, take turns, agree and verify.
  • Swarm has benefits, and sometimes we know that we will have peer interactions and need to manage them effectively.
  • To manage the lack of shared intent, shared context and shared reasoning that you will see with these agent teams, you need effective collaboration tools that close these gaps.

BACKUP. Source: AccordConcord_19Oct2026.pptx (Shift.forward(), Oct 27, 2026), slides 2 to 4. These are results on SRE triage (incident triage) for the full L9 protocols from the Internet of Cognition team, not for Mycelium's simplified versions. Say that first.

Accord card, "same meaning": before work starts, agents agree on the goal, the words and how "done" is checked. FIXES: the same word meaning different things (the source's example: a telemetry agent reports error_rate = 0.087 while a verifier checks error_rate > 5%, the same number with opposite meaning and no alert), agents with different ideas of the task, and nobody agreeing how success is verified.

Concord card, "same decision": when options diverge, the group commits only to a choice every agent can accept. FIXES: agents that state positions but make no proposals, conflicts that are never reconciled, and herding (agents agreeing because the others agreed, not because they checked).

"Work under the contract": the arrows show the order. Accord first, then the work happens under the agreed contract, and when options diverge during the work, Concord takes over. (In Mycelium the Accord output is a saved shared summary, not a locked contract.)

Results table, by column:

Converges: how often a run finishes with an outcome. Accord locks a contract in 83% of runs. Concord reaches a decision in 89%.

Gets it right: whether the outcome holds up. For Accord, 99.5% of the locked terms are used afterwards. For Concord, 98% of outcomes are satisfactory and 93% fair. CHECK how the source scored "satisfactory" and "fair" before you explain them.

Costs: tokens per run. Accord uses 379K prompt tokens, 85% cache eligible. Concord uses 876K per run, 87% cache eligible. Cache eligible means the share of the prompt that can be served from a cache. The source deck puts Concord at about 44 cents a run.

Pays off: what you get for the cost. For Accord, 81% glossary uptake (agents actually use the agreed terms) and 61% of terms visibly shape their reasoning. For Concord, 0.86 average worst-off satisfaction (how satisfied the least happy agent ended up) and 0 to 3 repairs (how many fix rounds were needed).

Bottom line: always converges (proven to end within the round budget and never cycle), cost known up front (a hard ceiling before the run starts), and ships as agent skills with no recompile. These are the source deck's claims about the full protocols. Mycelium's simplified versions don't carry them over automatically.

Mycelium's own small test (five runs each, September 2026, per the L9 integration page): aligner and Concord reached agreement 5 of 5. Concord's median was 60 seconds against the aligner's 156. Concord's agreements landed right at the bar of 70.
